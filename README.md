# LX인터내셔널 프리보딩 웹앱

신규 입사자에게 URL로 전달하는 입사 전 온보딩 페이지입니다.
이 문서는 **개발 지식이 없어도** 이 프로젝트를 인수인계받아 이해하고,
필요하면 직접 수정·배포까지 할 수 있도록 안내합니다.

---

## 1. 이 프로젝트는 무엇이고, 어떻게 돌아가나

### 무엇을, 왜

- **무엇**: 입사가 확정된 신규 입사자에게 링크 하나를 보내면, 첫 출근 안내(날짜·시간·장소·담당자),
  회사 소개, 준비물 체크리스트, 참고 정보(조직 문화·매너)를 모바일 화면으로 보여주는 페이지입니다.
- **왜**: 별도 앱 설치나 로그인 없이, 링크 클릭만으로 입사 전 안내를 한 번에 전달하기 위해서입니다.
  입사자별로 이름·출근일·담당자 정보가 자동으로 채워지고, 웰컴 기프트 배송지도 이 화면에서 받습니다.
- **현재 단계**: 프로토타입 단계로, 실서비스(정식) 전환 전입니다.

### 어떻게 운영되나 (전체 그림)

이 프로젝트는 서로 다른 두 곳에서 관리되는 두 조각으로 이루어져 있습니다.

| 조각 | 실체 | 있는 곳 |
|---|---|---|
| **화면(프런트엔드)** | `index.html` | 이 GitHub 저장소 → GitHub Pages로 자동 배포 |
| **DB + 서버(백엔드)** | Google Sheet + Google Apps Script(GAS) | `script.google.com` / Google Sheets (이 저장소 밖) |

```
입사자가 링크 클릭 (index.html#t=토큰)
   → 화면이 뜨자마자 Google Apps Script에 "이 토큰 정보 줘" 요청 (GET)
   → 이름·출근일·담당자·소속팀·환영메시지·제출여부를 받아 화면에 채움
   → 입사자가 배송지 폼을 작성해 "저장하기" 클릭
   → Apps Script로 전송 (POST) → Google Sheet에 한 행으로 저장
```

즉 **화면은 GitHub, 데이터는 Google**이라는 두 시스템이 API 하나로 연결된 구조입니다.
이 둘은 완전히 분리되어 있어서, 화면 코드(`index.html`)를 고쳐 push해도 Google 쪽은
전혀 바뀌지 않고, 반대로 Google Sheet에 입사자를 추가해도 화면 코드를 고칠 필요가 없습니다.

## 2. 가장 중요한 파일 두 개

이 프로젝트에서 실제로 "동작"을 담당하는 파일은 아래 두 개뿐입니다. 나머지는 이미지·문서입니다.

| 파일 | 무슨 역할을 하나 | 왜 중요한가 |
|---|---|---|
| [`index.html`](index.html) | 입사자가 실제로 보는 화면 전체. HTML 구조, 디자인(CSS), 동작 로직(JS)이 **한 파일 안에 전부 인라인**으로 들어있습니다. 빌드 과정 없이 이 파일 하나가 곧 배포되는 사이트입니다. | 이 파일을 고쳐서 `main` 브랜치에 push하는 순간 **실제 입사자가 보는 화면이 바로 바뀝니다.** 오타 하나, 색상 하나까지 전부 여기서 나옵니다. |
| [`docs/gas-code.gs`](docs/gas-code.gs) | Google Apps Script 백엔드 코드의 **사본**. 토큰으로 입사자 정보를 조회(`doGet`)하고, 배송지 폼을 Sheet에 저장(`doPost`)하고, 담당자가 새 입사자 링크를 만들 때 쓰는 메뉴 기능(`generateTokensAndLinks`)이 들어있습니다. | **이 파일을 고쳐서 push해도 실제 서버는 바뀌지 않습니다.** 실제로 동작하는 코드는 `script.google.com`에 별도로 배포되어 있는 완전히 다른 사본이기 때문입니다. 여기 있는 건 "기록·리뷰용 원본"이고, 실제 반영은 사람이 수동으로 옮겨야 합니다 (자세한 절차는 [3-3](#3-3-gasgoogle-apps-script-코드-수정하고-배포하기) 참고). |

그 외 파일:

```
lx-onboarding/
├── index.html                # 위 표 참고 — 운영 화면 (유일한 버전)
├── assets/
│   ├── logo-white.png        # 화면 상단에 쓰이는 반전 로고
│   ├── logo_front-square.png # 브라우저 탭 아이콘(파비콘)
│   └── 하이렉스.gif           # 마스코트 이미지
└── docs/
    ├── gas-code.gs                        # 위 표 참고
    ├── DECISIONS.md                       # "왜 이렇게 만들었나" 설계 근거 (→ 8번 요약)
    ├── ARCHITECTURE_DECISION_RECORD.html  # GAS 연동 아키텍처 결정 기록 (→ 8번 요약)
    └── ACCOUNT_OWNERSHIP_RECORD.html      # 계정 소유권 관리 방안 (→ 8번 요약)
```

## 3. 인수인계: 이어서 작업하려면

### 3-0. 시작 전에 필요한 접근 권한

담당자가 바뀌면 아래 두 가지를 반드시 이전 담당자에게 인계받아야 합니다. 이 두 개가 없으면
화면도 데이터도 손댈 수 없습니다.

1. **GitHub 저장소 접근 권한** — Organization `lxintl-onboarding`의 저장소 `preboarding`에
   Collaborator(또는 Organization 멤버)로 초대받아야 push가 가능합니다. 초대 전에는 코드를
   내려받아볼 수만 있고 온라인 반영은 못 합니다.
2. **Google 계정 접근 권한** — Sheet와 Apps Script는 이 프로젝트 전용 Google(Gmail) 계정으로
   운영됩니다. 이 계정 로그인 정보 또는 Sheet 편집자 권한을 이전 담당자에게 받아야 합니다.
   계정을 왜 이렇게 관리하는지는 [8번](#8-권한계정구조와-아키텍처-더-깊은-배경) 참고.

아래 3-1·3-2는 **화면(`index.html`)**을 고치는 두 가지 방법이고, 3-3은 **GAS 코드**를
고치는 방법입니다. 목적에 맞는 절만 읽으면 됩니다.

### 3-1. 깃허브 웹에서 코드 수정 및 배포하기 (개발 도구 설치 없이)

간단한 문구·색상 수정처럼 로컬 미리보기가 꼭 필요하지 않은 작업에 적합합니다.
Git이나 편집기를 설치하지 않고 브라우저만으로 끝낼 수 있습니다.

1. 브라우저에서 저장소 페이지(`github.com/lxintl-onboarding/preboarding`)에 접속해 로그인합니다.
2. 고치고 싶은 파일(예: `index.html`)을 클릭해 엽니다.
3. 오른쪽 위 연필(✏️) 아이콘을 클릭하면 편집 모드로 바뀝니다.
4. 원하는 내용을 수정합니다. (Ctrl+F로 문구를 찾아 고치는 방식이 가장 안전합니다.)
5. 화면 아래로 스크롤하면 "Commit changes" 영역이 나옵니다.
   - 위 칸에 "무엇을 고쳤는지" 짧게 한글로 적습니다.
   - **"Commit directly to the `main` branch"**가 선택되어 있는지 확인하고 커밋 버튼을 누릅니다.
6. 커밋과 동시에 GitHub Pages 배포가 자동으로 시작되어 **약 1분 이내**에 실제 사이트에 반영됩니다.

**주의할 점**

- 웹 편집 화면은 **로컬 미리보기가 불가능**합니다. 코드가 문법적으로 깨지면(예: 태그를 잘못
  지움) 바로 실사이트에 반영되므로, 텍스트·색상 변수 값처럼 **눈으로 결과를 예측할 수 있는
  수정에만** 이 방법을 쓰는 것을 권장합니다. 로직(JS)이나 레이아웃(CSS) 구조를 바꿔야 한다면
  3-2(로컬 작업) 방식으로 먼저 화면에서 확인하고 올리세요.
- 우편번호(주소) 검색 기능처럼 로컬 `file://`에서 동작하지 않는 기능은 애초에 웹 편집만으로는
  직접 테스트할 방법이 없습니다 — 3-2의 로컬 서버 절차를 이용하세요.

### 3-2. 컴퓨터에 저장소를 내려받아 수정하고 배포하기 (git 사용)

로직 변경, 레이아웃 조정처럼 미리 눈으로 확인하고 올려야 하는 작업에 적합합니다.

**준비물 (처음 한 번만)**

- **Git** 설치: https://git-scm.com/downloads (설치 후 터미널에서 `git --version`이 나오면 성공)
- 위 3-0에서 받은 **GitHub Collaborator 권한**
- **코드 편집기**: VS Code 추천 (https://code.visualstudio.com/)

**저장소 받아오기 (최초 1회)**

```bash
git clone https://github.com/lxintl-onboarding/preboarding.git
cd preboarding
```

**작업 시작 전, 항상 최신 상태로 맞추기**

다른 사람이 먼저 수정해서 올렸을 수 있으므로, 코드를 고치기 전에 매번 실행합니다.

```bash
git pull
```

**로컬에서 미리 확인하기**

`index.html`을 더블클릭해서 브라우저로 열어도 대부분 동작하지만, **주소 검색 기능은
`file://`로 열면 동작하지 않습니다.** 아래처럼 로컬 서버를 띄워 확인하세요.

```bash
python3 -m http.server 8000
```

브라우저에서 `http://localhost:8000` 접속. 서버를 켜둔 채로 에디터에서 `index.html`을
고치고 새로고침하면 바로 결과를 볼 수 있습니다.

- **문구(텍스트)**: HTML 안에 한글 그대로 들어있습니다. Ctrl+F로 검색해 수정하면 됩니다.
- **색상**: 직접 색 코드를 쓰지 말고 파일 상단 `:root { ... }`의 CSS 변수(`--brand`, `--gold`
  등)를 수정하세요. 어디서 쓰이든 한 번에 바뀝니다.
- 그 외 구조·로직 설명은 [`CLAUDE.md`](CLAUDE.md)의 "주요 JS 로직" 표를 참고하세요.

**수정 내용 저장하고 온라인에 반영하기 (commit & push)**

```bash
git status                              # 어떤 파일이 바뀌었는지 확인
git add index.html                      # 이번에 올릴 파일을 담아둠
git commit -m "환영 인사 문구 수정"       # 무엇을, 왜 고쳤는지 한 줄 메모와 함께 확정
git push                                 # GitHub에 실제로 반영
```

`push`한 순간 GitHub Pages가 자동으로 반영합니다 (약 1분 이내, 별도 승인 절차 없음).
그래서 **push 전에 반드시 로컬에서 눈으로 확인**하는 습관이 중요합니다.

### 3-3. GAS(Google Apps Script) 코드 수정하고 배포하기

이 프로젝트에서 가장 헷갈리기 쉬운 부분입니다. `docs/gas-code.gs`를 고쳐서 `git push`를
해도 **실제로 동작하는 서버는 전혀 바뀌지 않습니다.** GitHub는 코드를 텍스트로 보관할
뿐이고, 실제 서버는 `script.google.com`에 별도로 배포된 완전히 다른 시스템이기 때문입니다.
둘을 맞추는 건 사람이 수동으로 해야 합니다.

**절차**

1. `docs/gas-code.gs`를 이 저장소에서 먼저 원하는 대로 수정합니다 (git 기록을 남기기 위함).
2. 실제 Google Sheet를 열고 상단 메뉴 **확장 프로그램 → Apps Script**를 클릭합니다.
3. 열린 스크립트 편집기에 1번에서 고친 내용을 그대로 옮겨 붙여넣습니다.
4. `Ctrl+S`(또는 저장 아이콘)로 저장합니다.
5. **배포 → 배포 관리**를 클릭합니다.
6. 기존 배포 항목의 연필(편집) 아이콘 클릭 → 버전을 **"새 버전"**으로 선택 → 배포합니다.

   ⚠️ **주의**: 여기서 실수로 "새 배포"를 만들면 URL이 새로 발급되어 `index.html`의
   `GAS_ENDPOINT`와 어긋나 버립니다. **반드시 기존 배포를 "편집"해서 새 버전으로 올리세요.**
   URL이 바뀌면 안 됩니다.
7. 배포 후에는 화면부터 열어보지 말고, 브라우저 주소창에 `GAS_ENDPOINT?t=아무_토큰`을 직접
   입력해서 JSON 응답이 정상적으로 나오는지 먼저 확인하세요. (`GAS_ENDPOINT` 값은
   `index.html`에서 찾을 수 있습니다.)
8. 이 저장소의 `docs/gas-code.gs`가 실제 배포된 코드와 항상 같은 상태를 유지하도록
   관리하세요. (이미 1번에서 옮겼다면 그대로 커밋·push하면 됩니다.)

```bash
git add docs/gas-code.gs
git commit -m "GAS: 배송지 폼 필수값 검증 추가"
git push
```

**Sheet 구조를 바꿀 때 주의**: `docs/gas-code.gs`는 Sheet 1행(헤더)의 텍스트를 이름으로
찾아서 열 위치를 파악합니다 (`입사자`, `출근일`, `담당자`, `담당자연락처`, `소속팀`,
`환영메시지` 등). **Sheet에서 헤더 이름을 바꾸거나 열을 삭제하면 스크립트가 통째로
깨집니다** (특정 입사자 한 명이 아니라 전체가 영향받습니다). 헤더를 바꿔야 한다면
`gas-code.gs` 안의 `COL` 값도 반드시 같이 고치고, 위 절차대로 재배포하세요.

## 4. 새 입사자를 추가하려면 (코드 수정 아님, 반복 업무)

이건 3번과 달리 **HTML도 GAS 코드도 건드릴 필요가 없는** 일상 업무입니다.

1. Google Sheet에 입사자 행 추가 (이름, 출근일 등 입력)
2. 시트 메뉴 **"온보딩 관리 → 새 입사자 링크 생성"** 실행
   (`docs/gas-code.gs`의 `generateTokensAndLinks()` — 이름은 있는데 토큰이 비어있는 행만 채웁니다)
3. 자동 생성된 개인화 링크(`index.html#t=토큰&name=...&date=...`)를 입사자에게 전달
4. 입사자가 링크로 접속하면 이름·출근일·담당자·소속팀 정보가 자동으로 채워지고,
   배송지 제출 여부도 기기를 바꿔도 유지됩니다

**"동료들의 환영 인사"**는 Sheet의 `소속팀`, `환영메시지` 열 값으로 채워집니다.
`환영메시지`는 비워둬도 되며(팀에서 나중에 받아 채우는 값), 비어있으면 이름·소속팀을
자동으로 넣은 범용 문구로 대체됩니다. 자세한 우선순위 규칙은 [`CLAUDE.md`](CLAUDE.md)를 참고하세요.

## 5. 자주 바꾸는 값

**미리보기 기본값** — 토큰 없이 `index.html`을 그냥 열었을 때만 보이는 값입니다.
실제 입사자에게는 위 4번 절차로 개인화된 값이 자동 채워지므로 평소엔 건드릴 일이 없습니다.

```javascript
var FIRST_DAY  = '2026-06-22';
var FIRST_TIME = '오전 9:00까지';
```

**폼 저장 연동** — `index.html`의 `GAS_ENDPOINT`에 배포된 Apps Script 웹앱 URL이
연결돼 있습니다 (현재 연동 완료). 비워두면 미리보기 모드(로컬 저장만)로 동작합니다.

## 6. 실수했을 때 되돌리기

아직 push하지 않았다면(로컬에서만 고친 상태) 그냥 파일을 다시 열어서 직접 되돌리거나,
아래 명령으로 마지막 커밋 이후 변경을 전부 취소할 수 있습니다.

```bash
git status                    # 뭐가 바뀌었는지 먼저 확인
git checkout -- index.html    # index.html을 마지막 커밋 상태로 되돌림 (저장 안 한 내용은 사라짐)
```

이미 push까지 해버렸는데 잘못됐다면:

```bash
git log --oneline                   # 최근 커밋 목록과 짧은 해시(ID) 확인
git revert <되돌리고_싶은_커밋의_해시>
git push
```

`git revert`는 예전 상태로 강제로 밀어버리는 게 아니라, "그 변경을 취소하는 새 커밋"을
추가하는 안전한 방법입니다. 기록이 남아서 나중에 무슨 일이 있었는지 추적하기도 좋습니다.
잘 모르겠으면 무리해서 혼자 해결하려 하지 말고 이전 담당자나 팀에 커밋 해시와 상황을
공유하고 문의하세요.

## 8. 권한·계정 구조와 아키텍처 (더 깊은 배경)

인수인계 시 "누가 무엇을 소유하고 있는지", "왜 이런 방식으로 만들었는지"가 가장
헷갈리기 쉬운 부분입니다. 아래 문서들이 그 배경을 담고 있습니다. 요약만 읽어도
큰 그림은 파악되지만, 실제로 계정을 넘겨받거나 아키텍처를 바꿔야 한다면 원문을
꼭 읽어보세요.

### [`docs/ACCOUNT_OWNERSHIP_RECORD.html`](docs/ACCOUNT_OWNERSHIP_RECORD.html) — 계정은 누구 명의로 되어 있나

- GitHub·Google 계정 모두 **회사의 정식 유료 계정이 아니라, 이 프로젝트 전용으로 만든
  개인/무료 계정**으로 운영됩니다. "무료로 운영된다"는 것과 "누구 명의로 되어있는가"는
  별개 문제라는 점을 짚고, 담당자가 바뀌어도 계정이 특정 개인에게 묶이지 않도록 하는
  방안을 다룹니다.
- GitHub은 **Organization(조직)** 형태로 만들어 Owner를 2명 이상 유지합니다 — Owner가
  1명뿐이면 GitHub이 그 사람의 조직 이탈 자체를 막기 때문에, 담당자 교체 시 문제가 될 수
  있습니다.
- Google(Sheet·Apps Script)은 **이 프로젝트 전용으로 새로 만든 Gmail 계정**(특정 개인
  명의 아님)으로 소유하고, 로그인은 관리자 1명만 하되 나머지 담당자는 Sheet를 편집자로
  공유받아 각자 계정으로 접근합니다.
- 유료(회사 정식 계정) 대신 무료 계정을 택한 이유, 그로 인해 감수한 한계, 확인·승인이
  필요한 항목까지 원문에 정리되어 있습니다.

### [`docs/ARCHITECTURE_DECISION_RECORD.html`](docs/ARCHITECTURE_DECISION_RECORD.html) — 왜 이 조합(GitHub Pages + GAS)인가

- 풀어야 했던 문제: 로그인 없는 익명 입사자가 배송지 정보를 안전하게 제출하고, 인사팀이
  바로 확인할 수 있어야 함.
- 채택한 조합: **GitHub Pages(파일 배포)** + **Google Apps Script(데이터 처리)** +
  **Google Sheets(저장소)** — 월 고정비 0원.
- 왜 다른 조합(Vercel/Netlify + 별도 DB, Power Automate 등)을 쓰지 않았는지, 입사자
  정보 입력부터 시트 반영까지의 흐름, 담당자 교체 시 무엇이 남는지, 승인·착수가 필요한
  항목까지 원문에 정리되어 있습니다.

### [`docs/DECISIONS.md`](docs/DECISIONS.md) — 화면·UX를 왜 이렇게 만들었나

단일 HTML 파일 구조, 진행률 UI를 세그먼트 바로 바꾼 이유, NEXT 뱃지로 할 일을 하나만
강조하는 이유, 카드 스타일을 인터랙티브/읽기전용으로 나눈 이유, 구비서류를 하위
체크리스트로 중첩한 이유, Daum 우편번호 서비스를 택한 이유 등 화면 설계 근거를 담고
있습니다. 화면을 되돌리거나 구조를 바꾸기 전에 먼저 읽어보는 것을 권장합니다.

파일 구조, 브랜드 컬러 변수, 주요 JS 로직과 각 함수의 역할, 코드를 고칠 때 주의해야 할
